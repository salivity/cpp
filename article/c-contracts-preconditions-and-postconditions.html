C++ Contracts: Preconditions and Postconditions

This article explores how the C++ programming language conceptualizes contracts to establish formal preconditions, postconditions, and assertions. It covers the foundational Design by Contract (DbC) paradigm, the syntactic and semantic mechanics of interface boundaries, the distinction between caller and callee obligations, evaluation modes, and how contract violations are processed by the runtime environment and static analysis tools.

The Foundation of Design by Contract

Contracts in C++ are rooted in the Design by Contract (DbC) paradigm, originally introduced by Bertrand Meyer. Under this model, software components interact based on formal, binding agreements. Functions declare prerequisites that callers must satisfy, and in return, they guarantee specific outcomes upon completion.

Rather than relying on informal comments or ad-hoc runtime checks that intermingle with business logic, C++ contracts integrate these boundaries directly into the language syntax and type system. This approach creates clear interfaces, improves code readability, and allows both compilers and static analyzers to reason formally about program correctness.

Preconditions: Caller Obligations

Preconditions define the valid states and inputs required before a function executes. Conceptually, a precondition is the caller's obligation and the callee’s assumption.

  • Responsibility: The caller must ensure that all precondition predicates evaluate to true prior to invoking the function.
  • Guarantee: The function implementation can execute under the assumption that these requirements are met, removing the need for defensive, redundant boilerplate checks within the function body.
  • Use Cases: Common preconditions include verifying that a pointer is not null, ensuring an index is within array bounds, or validating that an integer argument falls within a specific mathematical domain (such as requiring a non-zero denominator).

In contract proposals targeted for modern C++ (such as C++26), preconditions are typically declared on function signatures using syntax such as pre(condition).

Postconditions: Callee Guarantees

Postconditions declare what a function guarantees to be true upon its normal return. Conceptually, a postcondition is the callee's obligation and the caller’s guarantee.

  • Responsibility: The function implementation must satisfy the postcondition predicates before returning control to the caller.
  • Return Value Inspection: Postconditions often inspect the function’s return value. C++ contract designs provide a mechanism to name the returned result within the postcondition predicate so it can be validated against inputs or internal state.
  • Use Cases: Common postconditions include guaranteeing that a returned container is not empty, confirming that an output resource has been allocated, or verifying that a modified state maintains internal consistency.

In modern syntax designs, postconditions are designated on function declarations using forms such as post(result: condition), allowing direct reference to the resulting value.

Assertions and Invariants

Complementing preconditions and postconditions, contracts include internal assertions (often denoted as contract_assert). While preconditions and postconditions define external interface boundaries, assertions validate assumptions within the implementation itself at specific execution checkpoints. They confirm that internal invariants remain intact as execution transitions from input states to output results.

Contract Evaluation and Semantics

C++ contracts are conceptualized with configurable evaluation semantics to balance safety against performance overhead:

  1. Check and Enforce: The condition is evaluated at runtime. If the predicate yields false, a contract violation occurs.
  2. Ignore (Off): The condition is parsed and checked for syntactic and type validity, but no runtime code is emitted. This ensures zero runtime overhead in production environments while maintaining formal documentation.
  3. Assume: The compiler treats the contract condition as an axiom for optimization purposes, assuming it is always true without emitting evaluation code.

Violation Handling

When a contract check is evaluated at runtime and fails, program execution enters a standardized violation path. Instead of throwing standard C++ exceptions—which could break the contract framework's correctness guarantees—a contract violation invokes a designated violation handler.

By default, a violation typically terminates execution via std::abort() to prevent operation in an undefined or corrupted state. Implementations can also configure custom handlers to log diagnostic details—such as source location, failed condition text, and whether the failed contract was a precondition or postcondition—before termination or controlled recovery.
