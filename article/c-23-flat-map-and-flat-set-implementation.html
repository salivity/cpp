C++23 flat_map and flat_set Implementation

This article provides an overview of std::flat_set and std::flat_map, two container adaptors standardized in C++23. It explores their architectural implementation strategy, how they differ from traditional node-based associative containers like std::set and std::map, their underlying memory layout, and the performance trade-offs associated with cache locality, lookup speed, and element modification.

Container Adaptor Architecture

Unlike traditional C++ associative containers (std::set, std::map), which are node-based structures typically implemented as red-black trees, std::flat_set and std::flat_map are container adaptors. Rather than managing nodes and pointers directly, they wrap underlying sequence containers.

By default, both adaptors use std::vector as their backing storage, but developers can substitute any sequence container that provides random-access iterators, such as std::deque or custom contiguous allocators.

Memory Layout and Storage Strategy

The implementation strategy differs slightly between the set and map variants:

  • std::flat_set: Stores elements in a single sorted sequence container (e.g., std::vector<Key>).
  • std::flat_map: Implements a Structure-of-Arrays (SoA) layout by default. It maintains two distinct, parallel sequence containers: one for keys (std::vector<Key>) and one for mapped values (std::vector<Value>).

The SoA layout in std::flat_map provides significant cache benefits over an Array-of-Structures (AoS) layout (such as std::vector<std::pair<Key, Value>>). Because keys are packed tightly in contiguous memory, key searches do not load value data into CPU cache lines until a match is confirmed, substantially reducing cache thrashing.

Search and Lookup Efficiency

All lookups in flat containers utilize binary search algorithms (equivalent to std::lower_bound).

While both red-black trees and flat containers share an algorithmic time complexity of \(O(\log N)\) for lookups, flat containers perform considerably faster on modern hardware. Traditional trees involve node allocations scattered throughout memory, leading to pointer chasing and frequent CPU cache misses. In contrast, flat containers take full advantage of contiguous memory allocation, maximizing hardware prefetching and L1/L2 cache line utilization.

Insertion, Erasure, and Performance Trade-offs

The primary trade-off for cache-friendly lookups is the cost of mutation:

  • Insertions and Deletions: Inserting or removing elements requires linear time (\(O(N)\)) because elements must be shifted to maintain sorted order within the underlying contiguous array.
  • Bulk Insertion: To mitigate the cost of repeated single-element insertions, both containers provide constructors and insert functions that accept ranges. These functions insert elements all at once and perform a single sort and deduplication pass, reducing overhead from \(O(N^2)\) to \(O(N \log N)\).
  • Iterator Invalidation: Any operation that inserts or erases elements may invalidate iterators, references, and pointers to the elements, matching the invalidation rules of the underlying sequence container.

Ideal Use Cases

The standard flat container implementation strategy is optimal for workloads characterized by:

  1. Read-Heavy Scenarios: Frequent searches with infrequent insertions or deletions.
  2. Phase-Oriented Lifecycles: Applications where all elements are loaded and sorted during initialization, followed exclusively by lookups during execution.
  3. Small-to-Medium Datasets: Scenarios where the sheer speed of contiguous memory traversal outperforms tree balancing overhead, even for small modification batches.
