Hardware Destructive Interference in C++ Cache Lines

Hardware destructive interference, commonly referred to as false sharing, occurs when concurrent threads on different CPU cores modify distinct variables that reside within the same hardware cache line. This article explores the mechanics of cache coherence, examines how destructive interference degrades multithreaded performance in C++, and explains how to detect and eliminate this bottleneck using modern C++ alignment techniques.

The Mechanism of False Sharing

Modern processors do not read from or write to system memory in individual bytes. Instead, memory subsystems transfer data in discrete blocks known as cache lines, which are typically 64 bytes in size on most x86 and ARM architectures.

When multiple CPU cores access memory, hardware cache coherence protocols (such as MESI or MOESI) ensure that data remains consistent across all processor caches. If Core A modifies a variable residing on a cache line, the coherence protocol marks that entire cache line as "invalid" or "modified" across the private caches of all other cores.

Destructive interference occurs when Thread 1 on Core A frequently updates Variable X, while Thread 2 on Core B frequently updates Variable Y, and both X and Y happen to reside within the same 64-byte boundary. Even though the threads are logically independent and do not share data, the hardware treats the entire cache line as shared.

Impact on Cache Line Performance

The consequences of destructive interference on multithreaded performance are severe:

  1. Constant Cache Invalidation: Every write from one core forces the other core to invalidate its local L1/L2 cache copy of the line. When the second core attempts to read or write its variable, it incurs a cache miss.
  2. Memory Bus Saturation: Frequent invalidations force the cores to continuously ping-pong the cache line back and forth across the interconnect or reload it from higher-latency shared L3 cache or main memory.
  3. Severe Latency Spikes: Instead of executing fast L1 cache accesses (typically 1–4 CPU cycles), the threads stall while waiting for cache coherence resolution, which can take tens to hundreds of cycles per operation.
  4. Negative Scalability: In high-concurrency systems, adding more threads to a task afflicted by false sharing often causes the application to run significantly slower than it would on a single thread.

Mitigating Destructive Interference in C++

Prior to modern C++ standards, developers resolved false sharing manually by estimating cache line sizes and inserting dummy byte arrays (padding) into structs. C++17 standardized this process by introducing compile-time constants in the <new> header:

  • std::hardware_destructive_interference_size: The minimum byte offset required to avoid false sharing between concurrent accesses.
  • std::hardware_constructive_interference_size: The maximum recommended size to ensure two objects fit on the same cache line to maximize spatial locality.

Applying alignas to Prevent Interference

You can eliminate false sharing by enforcing memory alignment on independently accessed data structures using the alignas specifier:

#include <new>
#include <atomic>

struct alignas(std::hardware_destructive_interference_size) ThreadData {
    std::atomic<uint64_t> counter{0};
};

ThreadData per_thread_counters[8];

By specifying alignas(std::hardware_destructive_interference_size), each ThreadData instance begins on a unique cache line boundary. Any padding necessary to prevent two adjacent instances from occupying the same line is added automatically by the compiler.

Local Aggregation

Another effective approach is minimizing frequent writes to shared state altogether. In multithreaded loops, threads should accumulate updates into local stack variables (registers) and write the final result to shared memory only once upon completion:

void worker(std::atomic<uint64_t>& global_counter, size_t iterations) {
    uint64_t local_sum = 0;
    for (size_t i = 0; i < iterations; ++i) {
        local_sum += compute();
    }
    global_counter.fetch_add(local_sum, std::memory_order_relaxed);
}

This pattern circumvents hardware destructive interference entirely by keeping frequent updates bound to core-private registers rather than contending over shared cache lines.
