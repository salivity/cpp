C++ const_cast: Purpose and Undefined Behavior Rules

In C++, const_cast is a specialized casting operator designed to add or remove the const or volatile qualifiers from pointers or references. While it serves a legitimate role in handling legacy APIs and reducing code duplication in member functions, misusing it to modify an originally immutable object invokes undefined behavior. This article explains the primary purposes of const_cast, provides practical examples of its valid implementation, and clearly delineates the exact circumstances that trigger undefined behavior.

The Purpose of const_cast

The primary role of const_cast<T>() is to adjust the cv-qualifications (const and volatile) of a type. Unlike static_cast or reinterpret_cast, const_cast is the only C++ cast operator that can safely strip away const semantics. It does not alter the underlying type of the variable or its binary representation.

Interfacing with Legacy or Poorly Designed APIs

A common use case involves interacting with older C libraries or third-party functions that accept non-const pointers (e.g., char*), despite never writing to the memory buffer:

void legacy_print_function(char* text);

void safe_wrapper(const char* message) {
    // Legacy API guarantees it only reads the buffer, but does not mark it const
    legacy_print_function(const_cast<char*>(message));
}

Avoiding Code Duplication in Overloaded Methods

Another standard pattern is implementing a non-const member function in terms of its const counterpart to avoid duplicating complex lookup logic:

class TextBuffer {
    std::string data;
public:
    const char& get_char(size_t index) const {
        // Assume bounds checking or other logic occurs here
        return data.at(index);
    }

    char& get_char(size_t index) {
        // Reuse the const version and cast away constness from the return reference
        return const_cast<char&>(std::as_const(*this).get_char(index));
    }
};

When const_cast Causes Undefined Behavior

Using const_cast to cast away const is legal. The critical boundary where undefined behavior occurs is the point of modification, not the cast itself.

Modifying Inherently Const Objects

Undefined behavior occurs if you use const_cast to modify an object that was originally declared as const.

const int max_limit = 100; // Inherently const object

int* ptr = const_cast<int*>(&max_limit);
*ptr = 200; // UNDEFINED BEHAVIOR

Compilers are entitled to place inherently const objects into read-only memory pages (such as .rodata). Attempting to write to such memory can cause segmentation faults, hardware exceptions, or silent failures. Furthermore, the compiler's optimizer assumes values declared const never change and may optimize reads away by substituting the compile-time constant 100 wherever max_limit is referenced, leading to unpredictable program state.

Valid Modification of Non-Const Objects

If the original object was defined without the const qualifier, casting away a const reference or pointer to modify the object is well-defined:

int original_value = 10; // Non-const object

void modify_value(const int& ref) {
    int& mutable_ref = const_cast<int&>(ref);
    mutable_ref = 20; // Well-defined: original_value was not declared const
}

modify_value(original_value);

While well-defined by the C++ standard, this pattern violates the caller's reasonable assumption that passing by const& guarantees immutability. It should generally be avoided in modern C++ design in favor of explicit mutable interfaces or using the mutable keyword for internal caching and thread synchronization.
