Understanding the C++ [[assume]] Attribute

The [[assume]] attribute, introduced in C++23, provides a standardized way to give compilers optimization hints by asserting that a specific boolean expression holds true at a given point in execution. This article explores the intended usage of [[assume]], its syntax, how it differs from traditional runtime assertions, and how compilers leverage these assumptions to produce faster and more efficient machine code while highlighting the critical risks associated with its misuse.

The Purpose of [[assume]]

Modern optimizing compilers constantly attempt to deduce invariants—facts about code state that never change—to eliminate redundant operations, vectorize loops, and prune unreachable branches. However, compilers frequently lack whole-program visibility or context about domain-specific constraints.

Before C++23, developers relied on vendor-specific extensions like __builtin_assume(...) in Clang/GCC or __assume(...) in MSVC to communicate known invariants. The standard [[assume(expression)]] attribute unifies these mechanisms into a portable language feature designed exclusively to enable compiler optimizations.

How It Works

The syntax takes a conditional expression inside the attribute:

void process_data(int* ptr, int size) {
    [[assume(ptr != nullptr)]];
    [[assume(size > 0 && size % 4 == 0)]];
    
    // Compiler can safely vectorize or skip null checks
}

When the compiler encounters an [[assume]] statement, it treats the enclosed expression as guaranteed truth from that point forward. Crucially, the expression inside the attribute is an unevaluated operand. This means:

  • The code inside the expression is never executed at runtime.
  • Expressions with side effects (such as [[assume(x++ > 0)]]) will not perform those side effects.
  • No instructions are emitted for the assumption itself.

Common Use Cases

  1. Eliminating Redundant Branching and Bounds Checks: If a function receives a value constrained by an external contract, informing the compiler can remove defensive checks:

    int get_lookup(int index) {
    [[assume(index >= 0 && index < 256)]];
    return table[index]; // Bounds check can be safely omitted
}

  2. Facilitating Loop Vectorization and Unrolling: Compilers can generate SIMD (Single Instruction, Multiple Data) instructions if they know array sizes or trip counts meet alignment or divisibility constraints:

    void process_elements(int* data, int count) {
    [[assume(count % 8 == 0)]];
    for (int i = 0; i < count; ++i) {
        data[i] *= 2;
    }
}

  3. Pointer Properties and Invariants: Assumptions can specify pointer alignment or that two pointers do not alias each other.

[[assume]] vs. assert

A common misconception is treating [[assume]] as an alternative to assert. Their roles are fundamentally opposed:

  • assert is a defensive debugging tool designed to validate assumptions. If an assertion fails, the program halts immediately to prevent corruption.
  • [[assume]] is an optimization contract. It never checks values. Instead, it instructs the optimizer to proceed under the assumption that the condition cannot fail.

The Risk of Undefined Behavior

If an assumption evaluates to false during program execution, the result is immediate undefined behavior (UB).

Because the compiler assumes the condition is impossible to violate, it may discard code paths that handle the false case entirely. For example, assuming a pointer is non-null when it is actually null could cause the compiler to remove an upstream null check, leading to memory corruption or silent logic errors rather than a clean crash.

As a best practice, [[assume]] should only be used in performance-critical code where invariants are already guaranteed by architecture, validation layers, or preceding logic.
