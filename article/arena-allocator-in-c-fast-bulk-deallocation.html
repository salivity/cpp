Arena Allocator in C++: Fast Bulk Deallocation

An arena allocator, also known as a bump or region-based allocator, is a memory management mechanism that acquires a large contiguous block of memory upfront and serves smaller allocation requests by advancing an internal pointer. In C++, arena allocators achieve exceptionally high performance and instant bulk-deallocation by simply resetting this pointer back to the start of the block, bypassing the cost of individual heap deallocations and skipping per-object destructors. This article explains the internal mechanics of an arena allocator, how bulk-deallocation operates without invoking individual destructors, and the critical rules regarding object safety in modern C++.

How an Arena Allocator Works

Under standard memory management patterns, calling new or malloc incurs overhead because the runtime must search free lists, handle fragmentation, and maintain metadata headers for each individual allocation.

An arena allocator avoids this overhead entirely through a straightforward mechanism:

  1. Pre-allocation: The arena requests a large region of contiguous memory from the operating system or system heap (e.g., via std::malloc, mmap, or a static array) upon initialization.
  2. Sequential Bump Allocation: When an allocation is requested, the arena checks if enough contiguous space remains. It aligns the current offset to the required alignment of the target type, records the current memory address to return to the caller, and "bumps" the offset pointer forward by the size of the allocation.
  3. No Individual Frees: The arena does not support freeing individual allocations. Space cannot be returned piecemeal; memory is strictly consumed forward until the entire arena is reset or destroyed.

Because an allocation only requires alignment math and a pointer addition, it executes in \(O(1)\) time with virtually zero overhead and optimal cache locality.

The Mechanics of Bulk-Deallocation

Standard C++ deallocation with delete or standard containers performs two distinct steps:

  1. It calls the destructor (~T()) of the allocated object to clean up owned resources.
  2. It returns the underlying memory buffer back to the global allocator.

An arena allocator fundamentally changes this lifecycle. Bulk-deallocation occurs by setting the allocation offset back to zero (or the start of the buffer):

void reset() noexcept {
    offset_ = 0;
}

This single assignment instantly reclaims all memory previously allocated from that arena in \(O(1)\) time, regardless of whether it held ten objects or ten million objects. The underlying memory buffer remains mapped and ready to be overwritten by subsequent allocation requests.

Bulk-Deallocation Without Destructors

Because reset() merely moves an integer offset, the CPU never executes the destructor bodies of the objects residing within the arena. Understanding when this is valid is vital in C++.

1. Trivially Destructible Types

The C++ standard classifies a type as trivially destructible if its destruction entails no side effects. This applies to:

  • Scalar types (e.g., int, float, pointers).
  • Arrays of trivially destructible types.
  • Plain Old Data (POD) structs and classes whose member variables and base classes are also trivially destructible, and which declare no custom destructor.

For trivially destructible types, calling a destructor is an absolute no-op; the compiler emits no machine code for ~T(). Consequently, failing to invoke destructors for these types has zero negative side effects. The arena simply reclaims the raw bytes, and no memory or resource leaks occur.

In modern C++, you can enforce this requirement at compile time using type traits:

static_assert(std::is_trivially_destructible_v<T>, 
              "Types allocated in this arena must be trivially destructible.");

2. The Danger of Non-Trivial Types

If an object manages external resources—such as heap memory (std::string, std::vector), file descriptors (std::fstream), or synchronization primitives (std::mutex)—skipping its destructor creates a resource leak. The arena reclaims the bytes occupied by the container itself, but the external buffer owned by the container is never freed.

When non-trivially destructible objects must be used within an arena, systems typically rely on one of two solutions:

  • Destruction Chains: The arena maintains a linked list or dynamic array of function pointers that invoke ~T() for non-trivial types during reset(). While this re-introduces linear iteration overhead, it isolates that overhead strictly to types that require it.
  • Arena-Aware Containers: Using custom container implementations that also allocate their internal dynamically sized buffers from the same arena. When the arena resets, both the container header and its contents are reclaimed together without standard heap allocations.

Minimal C++ Arena Implementation

Below is a minimal, practical arena allocator that supports alignment and placement construction for trivially destructible types:

#include <cstddef>
#include <cstdint>
#include <new>
#include <type_traits>
#include <utility>

class ArenaAllocator {
public:
    explicit ArenaAllocator(std::size_t capacity)
        : capacity_(capacity),
          buffer_(static_cast<std::byte*>(::operator new(capacity))),
          offset_(0) {}

    ~ArenaAllocator() {
        ::operator delete(buffer_);
    }

    ArenaAllocator(const ArenaAllocator&) = delete;
    ArenaAllocator& operator=(const ArenaAllocator&) = delete;

    template <typename T, typename... Args>
    T* create(Args&&... args) {
        static_assert(std::is_trivially_destructible_v<T>,
                      "Arena cannot call destructors; T must be trivially destructible.");

        // Calculate alignment requirements
        std::size_t current_addr = reinterpret_cast<std::size_t>(buffer_ + offset_);
        std::size_t alignment = alignof(T);
        std::size_t aligned_addr = (current_addr + (alignment - 1)) & ~(alignment - 1);
        std::size_t new_offset = (aligned_addr - reinterpret_cast<std::size_t>(buffer_)) + sizeof(T);

        if (new_offset > capacity_) {
            throw std::bad_alloc();
        }

        offset_ = new_offset;
        return ::new (reinterpret_cast<void*>(aligned_addr)) T(std::forward<Args>(args)...);
    }

    void reset() noexcept {
        offset_ = 0;
    }

private:
    std::size_t capacity_;
    std::byte* buffer_;
    std::size_t offset_;
};

Ideal Use Cases

Arena allocators thrive in environments with distinct operational phases and bounded lifetimes:

  • Game Development: Per-frame allocators instantiate render queues, particles, or transient physics calculations. The arena is reset at the end of each frame with zero destructor overhead.
  • Network Servers: Per-request allocators handle deserialization and payload parsing. When an HTTP request completes, the entire request arena is cleared instantly.
  • Compilers and Parsers: Abstract Syntax Tree (AST) nodes and intermediate representation instructions are built rapidly during compilation phases and released simultaneously once code emission is complete.
